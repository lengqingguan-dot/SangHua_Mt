# 《夜出桑华山》画面、声音与剧情演出改造策划案

日期：2026-09-27。性质：供评审的改造方案，本轮不修改游戏代码、不批量生成素材。

## 1. 推荐方向与目标

推荐把现有游戏改造成“2D 场景探索＋立绘对话＋关键剧情 CG＋可视化回合战斗”的离线 RPG。继续使用现有 JavaScript 游戏逻辑，先升级表现层。首个交付物称为“视觉化试作版”，暂不挤占既定 0.3.0 肢体玩法版本号。

玩家进入矿井时看见矿道背景，听见滴水和远处敲击声；与 NPC 交流时出现人物立绘、表情和底部对话框；重要情节切换到专用 CG；战斗时点击敌方形象锁定，技能用短动画和音效反馈。装备、技能原典和研习册继续由副本怪物／首领概率掉落，拾取后在背包处理。《仇恨》开局自带，其他技能通过原典学习，在下方技能栏查看和升级。

首期的“有画面”指上述完整演出能力，不承诺同时加入自由行走、即时动作战斗、3D、全角色骨骼动画或全剧情配音。它们需要各自的玩法和素材预算。

## 2. 已核对的项目基础

本方案依据当前工作区代码，而非从零假设一个新项目：

| 现有部分 | 已有能力 | 改造重点 |
| --- | --- | --- |
| `index.html`、`ui.js` | 多面板界面，DOM 输出，下一句和遮罩 | 增加中央视觉舞台、统一对话框和音量设置 |
| `game/story.js`、`game/storyEngine.js` | 任务／事件注册、条件判断、逐行播放、跳过、完成回调 | 把字符串升级为带说话人、表情、画面、声音的结构化演出 |
| `characters/`、`game/npcSystem.js` | NPC 台词、人物介绍、立绘显示与放大 | 立绘进入对话舞台，增加表情、站位与角色名 |
| `world/`、`game/look.js`、`game/movement.js` | 房间连接、场景物品、NPC 与移动 | 按房间 ID 显示背景、环境声和可点击热点 |
| `game/battle.js`、`game/combatTargeting.js` | 回合战斗、稳定敌方实例 ID、单目标锁定 | 敌方站位、锁定描边、受击和技能动画 |
| `game/exploration.js`、`game/pickup.js` | 副本进出、死亡概率掉落、地面拾取 | 把掉落图标与拾取反馈接入视觉舞台 |
| `game/saveSystem.js` | v4 存档、剧情状态、战中状态与动态物品 | 增加可序列化的演出进度，确保播放和游戏结算分离 |

素材目录目前有 104 个 PNG 文件，其中人物立绘文件 11 个，包括角色状态变体。它们不是 104 张可直接用于场景的图，也不能据文件存在就认定风格、分层和内容均可复用。本轮只核对了文件与引用，尚未逐张做视觉验收。代码与素材检索未发现现成的音频文件或统一音频管理器。

当前剧情不全在 `story.js`：NPC 台词、贫民窟任务、场景交互、物品事件也有独立播放或直接输出。因此不能只替换一个打印函数就宣称完成全游戏视觉化。

## 3. 技术路线选择

| 路线 | 适合的最终形态 | 本项目迁移工作 | 建议 |
| --- | --- | --- | --- |
| 继续 HTML/CSS/JavaScript | 场景点击、立绘对话、CG、回合战斗 | 复用核心状态和规则，重构演出与界面 | 首期采用 |
| Ren’Py／Python | 剧情与分支占绝大多数的视觉小说 | 剧情表达方便，但现有背包、动态地图、战斗和存档仍需移植 | 仅在决定让游戏以阅读剧情为主时采用 |
| Godot／GDScript | 可走动的 2D 地图、角色动画、物理或更复杂战斗 | 重写前端和大量逻辑，导入数据并重新验证存档 | 确定自由移动是长期核心后再评估 |

Ren’Py 官方入门展示了对话、背景、立绘、转场以及默认存读档能力；这能减少视觉小说基础功能的工作量，但不等于能直接运行现有 JS RPG。[Ren’Py 官方入门](https://www.renpy.org/doc/html/quickstart.html)

Godot 支持导出 Windows 可执行程序与资源包，能够满足离线分发需求。是否迁移应由玩法决定，单纯增加 CG 和声音不构成必须重写的理由。[Godot Windows 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

建议执行顺序：先完成 JS 视觉化试作，再根据实际游玩效果决定是否需要角色自由行走。未来若换引擎，结构化剧情、素材清单、道具和技能数据可以继续使用；DOM 界面、JS 回调和现有存档不能假设自动兼容。

## 4. 玩家界面与交互

### 4.1 场景探索

采用 16:9 的视觉舞台，设计基准 1920×1080，兼容 1280×720。中部显示背景，人物和交互物位于画面中的指定位置；底部保留背包、技能、装备、任务和菜单。方向导航继续使用现有房间连接，避免为了画面改造改变剧情路线。

每个场景包括背景、可选前景、NPC 热点、物品热点、出口和环境声。热点使用相对坐标，窗口缩放后仍与画面对齐；鼠标悬停显示名称，键盘可遍历。原“周围可见”列表可作为辅助入口，不能要求玩家凭眼力找像素级道具。

地图上共享建筑结构的普通房间可以共用背景；用灯光、前景和物件变化区分。主线节点、首领房和特殊地点优先拥有独立画面。

### 4.2 对话与旁白

- 对话框显示说话人和台词；旁白不强行配人物名。
- 同屏常用 1～2 名角色，最多 3 名。当前说话者提亮，其他角色轻微压暗。
- 点击或空格：文字未显示完时补全本句，已显示完时进入下一句。
- 支持自动播放、已读快进、隐藏对话框、历史记录、音量和文字速度。
- 普通台词每屏控制在约 25～70 个汉字，按语义断句；重要停顿由演出数据表达，不依赖写满省略号。
- 历史记录只回看文本，不回滚游戏状态；关键选择出现时暂停自动播放和快进。

### 4.3 CG 使用规则

CG 是关键事件的专用画面，不是一句文字对应一张插图。首期以背景＋立绘承担约 80%～90% 的剧情画面，约 10%～20% 的重要演出节点使用 CG；此比例是制作预算建议。

适合 CG 的节点包括重大登场、发现关键道具、环境突变、剧情转折和章节结尾。优先选择能表达信息或情绪、难以用普通立绘表现的场面。CG 配合缓慢推近、局部光效和音效即可构成演出，不必每张都做成视频。

CG 欣赏页记录解锁 ID。回看不调用任务奖励、掉落、战斗启动或人物死亡回调。

### 4.4 战斗表现

复用现有回合和目标规则。普通敌人用半身或全身战斗图，首领使用专用图；同模板敌人保留序号与独立血条。点击形象锁定，描边、头顶标记和技能目标名称同时反馈；未指定时默认第一名有效敌人。

普攻表现为短促位移／挥击光效、命中特效、伤害数字与声音。技能再增加对应的色彩、轨迹或屏幕效果。数值计算只发生一次，动画播放速度不能创造额外行动。设置中允许加速和关闭震屏，视效结束或失败都应释放交互锁。

敌人倒下后，在其附近出现掉落物图标和名称；多件物品可汇总到地面列表，继续由玩家拾取。没有兑换货币、领取商店或首通奖励菜单。

## 5. 剧情转换方法与示例

### 5.1 三种处理方式

| 原文本用途 | 转换方式 | 需要人工决定的内容 |
| --- | --- | --- |
| 描写环境、人物外观 | 背景／立绘承担主要信息，旁白保留无法从画面判断的信息 | 哪些句子可压缩，哪些是线索 |
| 对话、内心活动、选择 | 对话框＋说话人＋表情＋可选配音 | 说话人、情绪、节奏与分支条件 |
| 关键事件或行动结果 | CG、音效、镜头运动，再返回探索或战斗 | 分镜、状态变更时点与表现强度 |

先清点事件，再标注角色和演出，再制作素材。自动脚本可以抽取文本和生成待标注表，但不能仅凭引号可靠判断所有说话人，也不能自动保证剧情和任务逻辑不变。

### 5.2 现有事件示例：莉娅娜发现血色宝石

采用原有 `blood_gem_liana` 事件作为非露骨演出示范。以下是建议分镜，不在本轮修改原任务。

| 镜头 | 画面 | 对话／旁白 | 声音及逻辑 |
| --- | --- | --- | --- |
| 1 | 训练场背景，莉娅娜立绘 | 她注意到你身上的血色宝石。 | 环境声延续，音乐降低 |
| 2 | 换警惕表情，视线朝向宝石 | 她的目光停住，手缓缓按上剑柄。 | 一次低沉提示音 |
| 3 | 宝石微光 CG，或道具特写 | 无台词，短暂停顿 | 轻微共鸣音 |
| 4 | 返回立绘，换紧绷表情 | 莉娅娜：“这东西……让我不舒服。” | 可选短句配音 |
| 5 | 武器抬起的非血腥剪影／立绘姿态 | 她拔出长剑。 | 出鞘声，短促转场 |
| 6 | 战斗舞台出现 | 显示目标与行动按钮 | 只启动一次战斗，切换战斗音乐 |

现有事件在 `onStart` 就调用 `startBattle('liana')`。改造时需要把战斗启动移到演出的明确边界，并处理旧脚本兼容；否则可能出现台词没播完，战斗已经结算的情况。跳过本段应直接到同一战斗边界，不能绕过触发，也不能启动两次。

## 6. 美术方案与素材制作

建议风格为统一的暗色奇幻 2D 插画：矿井偏冷灰、城镇偏旧暖色、遗址偏低饱和紫蓝，以少量高亮色突出可交互目标。此为提案，不代表已经确认当前 104 张图片的视觉风格可直接统一。

角色先建立一张设计基准图：脸型、发色、服装、武器、身高比例和配色固定，再用同一参考图生成表情与姿态。现有立绘如合适可作为参考；不能用不同提示词分别生图后默认它们长相一致。官方文档也明确说明连续生成可能出现角色一致性和构图偏差，最终仍需筛选与修正。[OpenAI 图像生成说明](https://developers.openai.com/api/docs/guides/image-generation)

### 6.1 视觉化试作素材预算

目标：20～30 分钟的可玩内容，覆盖矿井区域的一段真实剧情和封存支矿道。具体连接顺序遵守原任务，不为演出强行改地图。

| 素材 | 首期数量 | 制作规格与复用方式 |
| --- | ---: | --- |
| 场景背景 | 6 张基础背景＋2 张光照变体 | 矿井深处、通道、矿口、工作坊、训练场、支矿首领厅；普通通道复用 |
| 主要人物 | 艾莎、莉娅娜各 1 个基础姿态＋4 种表情 | 表情与身体尽量分层；主角首期采用第一人称，不追加完整主角动作集 |
| 敌方战斗图 | 3 张 | 掠夺者、投石手、藏械监工；同模板群战复用图但显示实例序号 |
| 关键 CG | 3 张 | 矿井开场、宝石共鸣、支矿道通关后的环境画面；不追加剧情奖励 |
| 常用图标 | 24 个 | 覆盖试作的装备、书籍、状态与操作，不代表全游戏图标总数 |
| UI | 1 套 | 对话框、姓名牌、菜单、战斗目标、掉落提示、设置 |
| 小型视效 | 6 组 | 命中、斩击、格挡、技能蓄势、升级、拾取；代码动画优先 |

背景和 CG 按 1920×1080 交付目标组织，实际生成后按构图裁切或适配，不能预设每次生成都精确符合交付尺寸。立绘使用透明 PNG／WebP，统一画布、脚底位置和可视尺寸。UI 文本由代码绘制，避免把字烘焙进图片。成品保留可编辑源文件与压缩后的运行资源。

### 6.2 我能协助生成什么

| 类型 | 可协助的工作 | 交付边界 |
| --- | --- | --- |
| 背景、人物立绘、装备／道具图、非露骨 CG | 生成草图、参考图改图、表情与姿态变体、素材整理与接入 | 当前会话有图像生成工具；一致性、透明边缘和游戏内显示仍需逐件验收 |
| UI、地图热点、文字排版、简单光效与动画 | 用 HTML/CSS/SVG/Canvas 实现 | 能交付可编辑代码；复杂骨骼动画需要额外分层与绑定工作 |
| 分镜、台词、配音表、音效清单 | 编写非露骨演出脚本，标注情绪、时长和触发点 | 不等于已制作录音或音乐文件 |
| 简单 UI 音效 | 可以通过程序合成基础提示音、轻微脉冲等 | 自然环境声、武器质感仍需录音或合适的素材来源 |
| 角色语音、BGM、复杂音效 | 制作需求、对接可用工具、整理和混音接入 | 当前没有已连接的专用音乐／配音生成工具，不能承诺此刻直接生成全部成品音频 |

如果后续使用 TTS 服务，可以在制作阶段生成音频文件，再随游戏打包。OpenAI TTS 文档列出中文支持并要求向使用者明确说明其为 AI 语音；正式采用前仍需试听中文咬字、角色区分和情绪表现。[OpenAI 语音生成说明](https://developers.openai.com/api/docs/guides/text-to-speech)

所有运行素材都提前生成并存入本地。玩家不需要 API 密钥、图像生成账户或联网来观看 CG、听配音。音色采用有权使用的预设或取得授权的录音，素材清单记录来源与使用条件。

## 7. 内容尺度与生成限制

可以协助开发有成人主题、复仇、压迫、恐怖气氛和战斗的游戏，以及对应的普通人物图、环境、武器和非露骨剧情演出。是否属于某个平台的“限制级”，与我能否生成某一张图、台词或音频，是两件不同的事；标注“18+”不会解除素材生成限制。本案不作正式年龄评级或平台上架结论。

现有项目包含成人性内容、尸体与肢体互动，以及部分带性意味的血腥描述。这些内容不能统一视为普通 RPG 动作场景，也不适合直接批量转成 CG。需要逐场景检查剧情目的和实际表现。

| 内容 | 本方案能提供的帮助 |
| --- | --- |
| 成年角色正常衣着立绘、阴暗环境、武器、战斗姿态 | 可以设计并协助生成 |
| 非露骨的受伤、死亡后果、恐怖暗示 | 可以按具体镜头评估，以叙事而非血腥特写为重点 |
| 露骨性行为、色情化身体展示、用于性刺激的音频 | 不能协助生成对应内容 |
| 性暴力、强迫性性行为、性化的尸体或肢解场面 | 不能按其露骨或色情表现制作 CG、演出文本或音频 |
| 以残肢、内脏、酷刑细节为重点的极端血腥特写 | 不能协助制作这种具体表现，可改为非露骨叙事 |
| 未成年人或儿童化人物的性内容 | 不能生成；虚构身份或仅补写成年年龄不构成例外 |

可选的改编方法是真正减少露骨内容：用角色反应、场景变化、道具和非详细的结果说明保留必要剧情信息；不详细展示伤害过程。仅把露骨画面盖黑或保留色情音轨，不属于有效的内容改编。未成年角色如参与普通剧情或非性化冒险，并不因此整体禁止创作。

这轮不会擅自删改原文。正式制作前按“可直接演出／需要非露骨改编／不纳入我可生成的素材范围”建立事件清单。可先完成正常场景和通用系统；不能把整包现有内容自动送去批量生成。

## 8. 音频设计

首期先做到有层次的声音，再增加配音。声音分为四条总线，分别有独立音量和静音开关：

| 总线 | 首期目标 | 播放规则 |
| --- | --- | --- |
| BGM | 探索、普通战斗、首领、重要剧情各 1 首，共 4 首 | 循环，切换淡入淡出；同一首跨房间不重新开始 |
| 环境 | 矿井滴水、风、工作坊等 4 条循环 | 与房间或区域关联，转场后清理上一组 |
| SFX | UI、脚步、金属、受击、拾取等约 12 个 | 控制同时播放数量，避免群战瞬间叠加失真 |
| VO | 2 名主要角色的 10～20 句关键台词，作为可选项 | 新句打断上一句；播放语音时音乐适度降低 |

语音可缺省，字幕必须完整。旁白首期以阅读为主，不要求每个菜单和战斗日志配音。AI 语音或录音完成后检查错读、尾音截断、音量差异和循环接缝。

浏览器可能阻止未经用户交互的有声音自动播放。因此“开始游戏／继续游戏”点击应负责初始化声音，并在播放被拒绝时保持游戏可用、提供开启声音按钮。[MDN 自动播放指南](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

窗口失焦默认暂停剧情自动推进并降低或暂停声音，回来后由玩家继续。音频加载失败不能让剧情卡住，快速跳过后不能继续播放旧台词。

## 9. 程序改造方案

### 9.1 模块划分

建议在现有工程内增加以下模块，名称仅为拟定：

| 模块 | 职责 |
| --- | --- |
| `VisualStage` | 背景、立绘、CG、热点与转场；不写入角色属性 |
| `DialoguePlayer` | 当前句、角色名、文字速度、已读记录、选择、自动和跳过 |
| `AudioManager` | 音频总线、循环、淡变、暂停、缺失素材处理 |
| `AssetRegistry` | 用素材 ID 查本地文件；预加载当前场景和下一段，避免一次加载全游戏 |
| `BattlePresenter` | 依据战斗事件显示攻击、命中、状态和掉落动画 |
| `StoryActionRegistry` | 将开始战斗、推进阶段等效果映射为稳定动作 ID，统一保证只执行一次 |

游戏状态仍是唯一事实来源。界面和声音只能表现已经确认的事件；换图、回看 CG、重播语音不能再次加属性、发物品或推进任务。

### 9.2 剧情数据示例

未来可将演出保存为如下结构，旧字符串先兼容为旁白：

```json
{
  "sceneId": "blood_gem_liana_intro",
  "revision": 1,
  "steps": [
    { "id": "s01", "type": "background", "asset": "bg_training_ground" },
    { "id": "s02", "type": "character", "character": "liana", "expression": "alert", "slot": "right" },
    { "id": "s03", "type": "say", "speaker": "liana", "text": "这东西……让我不舒服。", "voice": null },
    { "id": "s04", "type": "sfx", "asset": "sfx_sword_draw" },
    { "id": "s05", "type": "action", "actionId": "begin_blood_gem_liana_battle" }
  ]
}
```

动作 ID 必须在受控注册表中解析；表格不能注入任意 JS。剧情播放器只执行它负责的当前场景，旧计时器或被取消的演出不得继续推进。

### 9.3 作者编辑方式

结合此前希望用 Excel 编辑内容的需求，可把剧情分镜和素材清单设计成表格字段：`scene_id、step_id、type、speaker、text、background_id、character_id、expression、cg_id、bgm_id、sfx_id、voice_id、action_id`。复杂选择分支另设关联表，以稳定 ID 引用。

Excel 是作者编辑来源，开发工具校验后导出本地 JS 数据包。游戏运行时不解析 Excel、不连接数据库；继续使用普通脚本加载资源表，避免把本地文件读取能力作为玩家安装条件。原有函数型剧情先人工迁移，不把程序回调硬塞成电子表格单元格。

### 9.4 存档与跳过规则

新演出结构拟升级存档格式至 v5，保留 v4 导入。新增场景 ID、当前步骤 ID、分支结果、已执行动作 ID、CG 解锁记录与演出版本；不把 DOM、音频实例或函数对象放进存档。

存档优先落在完整句子或动作边界。对话中读取存档后，从该句重新显示，音乐按场景恢复；不要求精确恢复打字动画或音频毫秒位置。旧存档没有演出位置时返回当前房间安全边界，保留任务和战斗状态，不补播已经结算的奖励。

跳过时跳过的是文字动画和镜头等待，必要游戏动作仍按顺序执行一次；遇到未决定的选项必须停下。语音回看和 CG 回看完全使用只读演出路径。战中读档继续遵守当前暂停等待玩家恢复的行为。

## 10. 离线交付与性能

第一阶段保留浏览器入口：压缩包内含脚本、图片、音频和本地字体，断网打开 `index.html` 可玩。必须实际测试本地路径、中文目录、图片与音频格式；开发期工具依赖不能变成玩家依赖。

如需要“解压后双击游戏.exe”，可在视觉化稳定后使用 Electron 包装同一套资源，并实际交付可运行目录的 ZIP。Electron 的资源打包是额外构建步骤，不是给 HTML 改扩展名。桌面运行时会增加体积，应在试作阶段测量。[Electron 分发文档](https://www.electronjs.org/docs/latest/tutorial/distribution-overview)

桌面包装时只开放必要的存读档接口，保留浏览器导入／导出存档能力。旧 JSON 存档通过明确的导入迁移使用，不承诺浏览器本地设置自动进入桌面程序。

试作验收目标：基础画面不卡顿、常用交互响应约 100 毫秒内、场景切换不出现长时间空白、静态资源压缩包力争控制在 150 MB 内（不含桌面运行时）。这些是预算目标，需选定测试电脑后实测，不能作为当前性能结论。

## 11. 制作排期与难度

以下仅估算本文件限定的 20～30 分钟试作，假设 1 名熟悉项目的开发者，加持续参与的素材制作／校对。不是整部游戏重制报价，也不包含无限次美术返工。

| 阶段 | 工作与交付物 | 粗估有效工作量 |
| --- | --- | --- |
| 1. 清点与风格定稿 | 事件表、内容尺度标注、角色基准图、1 张背景和 UI 样板 | 3～5 人日 |
| 2. 演出基础 | 舞台、对话播放器、音频、旧脚本兼容、存档边界 | 10～15 人日 |
| 3. 试作内容接入 | 6 个基础场景、2 个角色、3 张 CG、1 个副本和战斗反馈 | 8～12 人日 |
| 4. 验收与打包 | 旧档、跳过、群战、声音、离线启动、性能与素材修正 | 5～8 人日 |

开发与集成粗估合计 26～40 人日；另预留约 10～20 人日制作、筛选和修正素材，可与开发部分并行。小团队可先按 6～10 周安排试作；一个人兼职时应按实际可投入工时换算。定稿后先做一段剧情和一个战斗房间，用实际产能校准剩余估算。

难度判断：只加背景和 BGM 较低；本方案完整试作为中等；全项目剧情逐段演出为中高，主要受台词整理、角色一致性、回调与存档兼容影响；更换引擎并加入自由移动为高。全游戏工期必须在剧情节点与所需独立背景清点完成后估算，不能按当前 104 张 PNG 数量推算。

## 12. 验收标准与首个可评审成果

首个成果应是一段可从头玩到尾的完整流程：进矿井、与角色对话、观看宝石事件演出、进入一次战斗、点击敌方锁定、进入支矿副本、取得掉落、拾取原典、背包学习、技能栏升级、保存退出、读档继续。

验收需要同时满足：

1. 对话中的显示完本句、下一句、自动、快进和历史记录不会重复触发游戏效果。
2. 场景切换、角色姿态与 CG 在小窗口下不遮挡关键操作；无素材时有可用的占位显示。
3. 普攻与攻击技能仍命中当前锁定敌人；动画加速和跳过不会增加攻击次数。
4. 掉落只生成一次，地面与背包状态存读档一致；重开前提醒未拾取物品。
5. 料理永久加成、初始《仇恨》、技能学习升级和旧档迁移继续通过已有回归。
6. 静音、音频失败、窗口切换和缺失配音都不会卡剧情；字幕不依赖声音。
7. 实际断网启动与一台没有开发环境的 Windows 电脑解压运行通过。
8. 素材来源、角色一致性和每段演出内容范围完成验收后，再复制流程到后续章节。

本轮交付本策划案；下一次实施可从“矿井背景＋艾莎／莉娅娜对话舞台＋一个战斗房间”开始。无需先重写整套游戏，也无需先生成全部剧情 CG。
